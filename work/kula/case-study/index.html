Overview

A system to scale the product.

Kula is the design system I built for Relyance AI, an enterprise data privacy and compliance platform. The goal was to create a systematic foundation that would allow the product team to scale with visual consistency, faster design velocity, and real collaboration between design and engineering.

I started the project alone, establishing the architecture and foundations. Over time, other designers joined and contributed to the documentation while I continued expanding the components.

Problem

A product without a system.

When I joined Relyance AI, the product had screen designs with UI elements but no systematized components. There was no design system file. Each screen was treated in isolation, with visual elements that were inconsistent with one another.
Engineering was already using a component library based on Google's Material 3, completely disconnected from the visual design. The gap between what was designed and what was implemented was evident.

Process

Foundations first

The process followed a clear logic: first everything components need to exist, then the components themselves, and finally the product-specific elements.

Phase 0 — Audit & Discovery

Review of the existing platform to establish a baseline before any design work began. The audit covered both the live product and available design files, evaluating visual consistency, component fragmentation, and accessibility compliance against WCAG 2.1 AA standards. Key findings included contrast ratio failures, inconsistent use of color and typography across surfaces, and the absence of a token layer or shared component structure. Usability heuristics were applied to identify recurring friction points in core flows. The audit output served as the foundation for prioritizing the token architecture and component roadmap in subsequent phases.

Phase 1 — Foundations

Definition of color, typography, and spacing tokens. Construction of the Figma variable system. The complete neutral palette, state colors, and a spacing scale based on a 4px grid were established.

Phase 2 — Base Components

Buttons, inputs, checkboxes, selects, switches, badges, modals, tooltips, drawers. Each component designed to visually align with the Material 3 components already in use in production but with his own voice.

Phase 3 — Business Components

Compliance tables, privacy dashboards, metric cards, data states. Elements that don't exist in any generic library because they respond to specific product needs.

File System Restructure

The main Figma file had become difficult to navigate. Icons and data visualization elements were separated into their own files, kept linked to the core through Figma libraries.

Collaborative Maintenance

Other designers joined to document while I continued creating new components. The system kept growing for at least 6 months after the initial build phase.

Challenges

Constraints That Shaped the System

Every design system runs into some version of the same problems: adoption, documentation, and scale. Kula was no exception, and each challenge had its own resolution arc.

.01

Adoption

Engineering adoption was willing but costly. There was no dedicated resource on the engineering side to implement the design system — every developer was absorbing it while still shipping features. Existing technical debt created constant friction. The system gained traction, but slowly, and always in competition with delivery pressure.

.02

Documentation

Storybook was explored as a bridge between design and code, but was ruled out due to technical constraints on the engineering side. Confluence was set up as an alternative, but never made it into the developers' actual workflow. Documentation ended up living primarily inside Figma — a pragmatic decision given the constraints, but one that limited its reach on the engineering side.

.03

Scale

As the system grew, the main Figma file accumulated enough pages to become slow and hard to navigate. The decision was to split icons and data visualization into separate files, linked back to the core through Figma libraries. The impact on working speed was immediate.

Outcome

What I've learned

Kula is one of the most complex design systems I've built. It's also the first in which I faced a problem hard to ignore: the distance between what gets documented and what actually gets adopted.

A design system without an adoption strategy is only half a product

Even when the Figma documentation was thorough, the engineering team struggled to balance their day-to-day tasks with implementing the new design. The solution was to create a workflow that minimized friction and built shared commitment on both sides, with a clear focus on adopting the new design system.
This required several sessions of intense discussion, identifying the right moments and features to bring in the new designs. A shared channel between design and engineering was created to keep the conversation in one place, and the design team committed to supporting developers throughout implementation and making the process as smooth as possible.

Coexistence is a design decision, not a limitation.

The constraint of not being able to redesign the entire platform pushed us to design components that could coexist with the existing ones. That ended up being a strength: Kula was never a world apart — it was a coherent extension of what was already built.

File architecture should be planned before it becomes a problem

The decision to split the system into three linked files improved the team's working speed as noticeably as any component I built. Structure is part of the system.

A system is never finished

Kula taught me that a design system is less a deliverable and more a living agreement between teams. The components, the documentation, the file structure — none of it matters if the people around it don't trust it or use it. The real work was building that trust.
